MAS Mentor Platform — Technical Guide (for Developers)
Scope: Architecture, data models, and APIs for the MAS mentor platform — the student-facing learning dashboard (roadmap, badges, XP) and the fulladmin panel (courses, modules, course-builder, batches, leads/CRM, Mr Test, Mr Learn, mapping).
Document version: 1.0 · Last updated: 2026-06-30 Codebase: mr-mentor-frontend/ (Next.js admin/mentor app) + mr-mentor-backend/ (Express +TypeORM API) Companion doc: MAS_PLATFORM_SALES_GUIDE.md (non-technical overview)
1. Architecture Orientation
Two frontends, one backend:
mr-mentor-frontend — the admin + mentor app (Next.js 15, App Router). Houses all authoring/management UI under src/app/admin/*, plus amentor leaderboard and user proﬁle.
Student learning portal — the student-facing dashboard (badges, XP/level/streak ribbon, batch roadmap with progress) is served by the backendunder /api/student/* but consumed by a separate portal (MAS_WEBSITE_URL = myanalyticsschool.com). The backend is multi-platform via an
x-platform header. So for the student dashboard, the source of truth in these repos is the backend response shapes, not React components in
mr-mentor-frontend.
mr-mentor-backend — Express + TypeORM over PostgreSQL. All admin routes gated by authMiddleware + adminMiddleware; the frontend injectsthe backend JWT via session.backendToken.
flowchart TB    ADMIN[mr-mentor-frontend\nadmin + mentor UI] -->|JWT| API[mr-mentor-backend\nExpress + TypeORM]    PORTAL[Student portal\nmyanalyticsschool.com] -->|/api/student/* + x-platform| API    API --> PG[(PostgreSQL\nschemas: default, mas_crm, mrtest, mrlearn)]    API -->|integration| EZ[EzExam\nexam engine = Mr Test]    API -->|integration| GR[Graphy\nLMS = Mr Learn]    API -->|AI calls| EL[ElevenLabs\nAarya voice agent]    API -->|e-sign| LG[Leegality\nMAS101 MOU]
Key architectural fact: Mr Test and Mr Learn are integration consoles, not home-grown engines. Mr Test proxies/syncs EzExam; Mr Learnproxies/syncs Graphy. The Sales CRM is fully native.
2. Core Domain Model & Mapping
The central relational ﬂow (entity names in mr-mentor-backend/src/entities/):
Lead / RawLead / CampaignLead / VendorLead   (CRM capture)   → User                                     (account)   → Application  (userId + batchId + courseId + status)        status: draft → submitted → under_review → approved                → payment_received → paid → batch_allocated → enrolled → deboardedBatch (code unique, courseId default, assignedModuleIds[], roadmapNotes, batchLeadId/cmId/superMentorId)   → Course (default; per-student override via Application.courseId)        → Module[]  (course_modules.courseId) → Class / Quiz / Assignment        → roadmapItems[]  (JSON on course; scheduleUnit, customTypes)Batch × roadmapItem:   → BatchMrLearnCourse (batchId, roadmapItemId, mrLearnCourseId, sequence, courseUrl)   → BatchMrTestExam    (batchId, roadmapItemId, mrTestExamId, sequence, prerequisiteCourseId, prerequisiteThreshold)   → roadmapNotes[itemId] = RoadmapNote[]   (per-batch session notes)Enrollment (userId + courseId, progress, moduleProgress)   ← classic LMS progressStudentProgress / XpEvent / StudentBadge                    ← gamification
A student "belongs to" a batch when they have an Application with batchId set and status in {ENROLLED, BATCH_ALLOCATED, PAID} (this exactset is used by BadgeService.resolveEnrolledBatchIds and getBatchRoadmap).

3. Roadmap
Where it lives: JSON on the Course entity (src/entities/Course.ts): - roadmapItems?: RoadmapItem[] (json) - roadmapScheduleUnit?:
ScheduleUnit (default 'week') - roadmapCustomTypes?: CustomRoadmapType[] (json)
Shared types: backend src/types/roadmap.ts, mirrored in frontend src/app/admin/mas/courses/components/types.ts.
RoadmapItem = { id, order, weekNumber, type, title,  description?, thumbnailUrl?, thumbnailS3Key?, links?[], attachments?[] }ScheduleUnit = "week" | "day" | "session" | "step"
Built-in item types (roadmapConstants.ts): MODULE 📘 , TEST 📝 , ASSIGNMENT ✏ , LIVE_CLASS 🎥 , WEBINAR 🎙 , PROJECT 🚀 , MILESTONE 🏁 .Custom types (label+emoji+color) persist in localStorage (mas.roadmap.customTypes.v1) via customTypesStore.ts and on the course(roadmapCustomTypes).
Authoring (RoadmapSection.tsx + RoadmapItemCard.tsx): - Ordering via @dnd-kit (handleDragEnd →  arrayMove →  re-stamp order); groupingby weekNumber; new item gets weekNumber = max + 1. - Thumbnails/attachments staged locally (_pendingThumbnailFile, _pendingFile), uploadedto S3 only at course save (uploadService.ts →  POST /api/admin/mas/courses/:id/roadmap/upload, POST
/api/admin/mas/batches/:id/roadmap/:itemId/notes/upload); S3 → CloudFront via toCdnUrl. - JSON import (JsonImportModal.tsx): single
{course, roadmap[]} or bulk array/{courses:[]} (max 50); parseAndValidate requires title + positive integer weekNumber; unknown type →warning, missing →  MILESTONE.
Batch overlay: Batch.roadmapNotes (json keyed by item id), plus BatchMrLearnCourse / BatchMrTestExam rows per roadmapItemId. Course deﬁnesthe skeleton; the batch enriches each item with real content + notes.
Student view: GET /api/student/batches/:batchId/roadmap (student.controller.getBatchRoadmap, ~line 2634, enrolled-only). Resolves thestudent's own course (Application.courseId overrides Batch.courseId) and returns { batchId, courseId, scheduleUnit, items, customTypes,
notes, batch, mrLearnByItem, mrTestByItem } where the *ByItem maps carry per-student progress, exam unlock (prerequisite gating), andsubmission state (buildMrLearnRoadmapForStudent / buildMrTestRoadmapForStudent).
4. Gamiﬁcation — XP, Levels, Streaks, Badges
Badges are statically deﬁned (code, not a DB table) in src/config/badges.config.ts — 6 starter badges:
id Name Criterion XP
first_step Explorer First daily_login XP event 25
profile_pro All Star User.isProfileComplete 25
week_warrior Momentum StudentProgress.longestStreak ≥ 7 50
test_taker Achiever First passing (≥50%) Mr Test on a batch-attached exam 50
mentor_connector Collaborator First COMPLETED mentor slot 50
module_master Scholar First completed Mr Learn module in a batch-attached course 50
Mechanics: - StudentBadge (src/entities/StudentBadge.ts) — one row per (userId, badgeId); unique UQ_STUDENT_BADGE makes unlockidempotent; seenAt gates the celebration modal. - BadgeService (src/services/BadgeService.ts) — listBadgesForUser, listUnseenBadgeIds,
markBadgesSeen, unlockBadge (idempotent insert + StudentProgressService.grantXp('badge_unlocked', baseOverride = xpReward)),
evaluateForUser, per-badge evalXxx. Batch-scoping: resolveEnrolledBatchIds, attachedMrTestExamIds, attachedMrLearnCourseIds. -Evaluation triggers: login (auth.controller.ts ~line 44), mentor-call completion (SlotCompletionService.ts), and the batch cron
src/workers/badgeEvaluation.worker.ts (paginates ENROLLED/BATCH_ALLOCATED/PAID users, page size 200).
XP/level/streak: src/config/xpRules.ts (event base XP, action milestones, multipliers, 5-level table L1=0 →  L5=2000, streak milestone every 7 days).
StudentProgress (cached snapshot: totalXp, level, currentStreak, longestStreak) + XpEvent (append-only ledger, dedup (userId,type,sourceId)).Migration: src/migrations/1762470000000-CreateXpAndBadges.ts.
Student API (studentProgress.controller.ts, routes student.routes.ts 47–50): GET /api/student/me/badges, GET
/api/student/me/progress (includes unseenBadges, blockingAxis, isOnFireToday), POST /api/student/me/badges/seen.
Disambiguation: @/components/ui/badge (shadcn) and PredictedInterestBadge.tsx (CRM) and NewCourse.metadata.badges (marketinglabels) are not gamiﬁcation badges.

7. Mr Test (EzExam integration)
Admin console for EzExam (myanalyticsschool.ezexam.in). Browse exams, push MAS students as test-takers, sync results back into MAS, attachexams to batch roadmap items (optionally gated by a Mr Learn course prerequisite).
Frontend src/app/admin/mrtest/: page.tsx (live exams GET /api/ezexam/online-exams), exams/[onexId], students/, create-student/,
synced/[configId] (cached snapshot), settings/ (auth + sync conﬁgs). Shared ?tag= ﬁlter from EzExam student tags.
Backend: routes src/routes/ezexam.routes.ts (mounted /api/ezexam); controllers ezexam.controller.ts (live pass-through) +
mrtestSync.controller.ts; services EzExamService.ts, MrTestSyncService.ts, MrTestTrainingDataService.ts.
Entities (schema mrtest): MrTestSyncConfig (one per synced exam: onlineExamId, batchId?, interval, enabled, lastRun), MrTestOnlineExam,
MrTestSubmission (marks/percentage/rank), MrTestSubmissionReport (question-level), MrTestSyncRun (audit). Cross-link: BatchMrTestExam
(default schema) — mrTestExamId + roadmapItemId + prerequisiteCourseId/prerequisiteThreshold (default 75%) + takeUrl.
Key endpoints: auth POST /auth/login|logout, GET /auth/status; live GET /online-exams, /online-exams/:onexId/detail, POST /proxy;students GET /students, POST /students/create-mas-account, GET /students/:rollnum/report; sync GET/POST /sync/configs, POST
/sync/configs/:id/run, POST /sync/batches/:batchId/run, POST /sync/by-tag.
"Synced" = results pulled (cached) into the mrtest schema via a MrTestSyncConfig + background runs (vs. the live "Online exams" home).
